# AGENTS.md — Nginx Log Explorer

## 1. Обязательное чтение

Перед любой задачей исполнитель должен прочитать:

1. `architecture.md`;
2. `AGENTS.md`;
3. `plan.md`;
4. только текущий файл `tasks/TASK-XXX.md`;
5. существующие тесты затрагиваемого модуля.

При конфликте требований остановиться и вернуть вопрос архитектору. TASK не может молча менять архитектуру.

## 2. Git-протокол

Одна TASK выполняется в одной новой ветке.

Перед началом исполнитель обязан:

```text
1. убедиться, что working tree актуального master чист;
2. обновить локальный master согласованным безопасным способом;
3. создать ветку task/TASK-XXX-short-name от актуального master;
4. подтвердить имя и базовый commit ветки в отчёте.
```

Правила:

- не начинать TASK из ветки предыдущей TASK;
- не выполнять merge/rebase в `master`;
- не force-push;
- не переписывать пользовательские изменения;
- до review архитектора не создавать финальный commit задачи;
- после `PASS` архитектора создать один commit с согласованными файлами;
- сообщение commit: `TASK-XXX: краткое описание`;
- merge выполняет только пользователь;
- следующая TASK начинается только от `master`, куда пользователь уже влил предыдущую.

Если среда исполнителя не позволяет оставить изменения без commit или обновить `master`, задача получает статус `BLOCKED` с точным объяснением.

## 3. Scope

- Реализовать только текущую TASK.
- Не делать unrelated refactor и «полезные заодно» функции.
- Не менять публичные контракты, структуру слоёв и выбранный стек без прямого требования.
- Не добавлять преждевременные abstraction layers для post-MVP возможностей.
- Соседнюю проблему не исправлять молча: описать её в отчёте.
- Не форматировать весь репозиторий из-за локального изменения.

## 4. Архитектурные границы

- React вызывает только HTTP API.
- API route не содержит SQL и основной бизнес-логики.
- Application service не зависит от React.
- Domain parser не зависит от FastAPI и SQLAlchemy.
- Persistence реализует repository contracts.
- Любой запрос записей scoped по `import_id`.
- Изменение API требует обновления схемы/типов и контрактных тестов в той же TASK.

## 5. Security

- Считать upload и каждую строку лога недоверенными.
- Не принимать путь к файлу от клиента.
- Не доверять filename, MIME type, IP, URL и user-agent из лога.
- Не использовать unsafe HTML rendering.
- Не строить SQL из пользовательских строк; сортировка только по allowlist.
- Соблюдать лимиты upload, длины строки, поля, pagination и query parameters.
- Не добавлять секреты, реальные персональные данные и production logs в код, fixtures, ZIP и отчёт.
- Не логировать raw log lines, query strings анализируемых запросов, IP и user-agent.
- Не ослаблять validation/CORS/escaping ради тестов.
- Новая зависимость допустима только при необходимости; её назначение указать в отчёте.

## 6. Миграции и данные

- Изменение схемы всегда сопровождается Alembic migration.
- Не редактировать уже применённую миграцию без отдельного указания.
- Тесты не используют рабочую SQLite database.
- Не включать DB-файлы и runtime uploads в review artifact.
- Destructive migration требует отдельного архитектурного review.

## 7. Testing

Обычная локальная TASK:

- добавить или обновить тест поведения;
- запустить тесты затронутого backend/frontend модуля;
- запустить релевантный typecheck/lint только для принятого scope.

Полный suite обязателен, если затронуты:

- migration/schema;
- общие API contracts;
- общая конфигурация или bootstrap;
- security primitives;
- release gate.

Запрещено заявлять проверки, которые реально не запускались. Падение существующего теста не удаляется и не обходится без анализа причины.

## 8. Review artifact

До review создать:

```text
TASK-XXX_CHANGED.zip
```

ZIP содержит только новые и изменённые в текущей ветке файлы относительно базового commit актуального `master`. Сохраняется структура путей.

Не включать:

```text
.git
.env*
node_modules
.venv
__pycache__
.pytest_cache
coverage
build
dist
logs
runtime
uploads
*.db
*.sqlite*
credentials
previous ZIPs
```

Перед отправкой вывести список ZIP и убедиться, что в нём нет секретов или runtime-данных.

## 9. Отчёт исполнителя

```text
TASK: TASK-XXX
STATUS: DONE / BLOCKED
BRANCH: task/TASK-XXX-short-name
BASE COMMIT: <sha>

Что сделано:
- ...

Изменённые файлы:
- ...

Решения и новые зависимости:
- ...

Проверки (только реально запущенные):
- команда → результат

Не сделано / риски / найденные соседние проблемы:
- ...

COMMIT: not created — awaiting architect PASS
ZIP: TASK-XXX_CHANGED.zip
```

## 10. Review outcome

- `PASS`: архитектор разрешает финальный commit текущего scope.
- `FAIL`: архитектор создаёт короткую `FIX-TASK-XXX-N`; commit запрещён до повторного review.
- После commit исполнитель возвращает SHA и прекращает работу. Merge и удаление ветки выполняет пользователь.
